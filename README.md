# Why your live-URL app is stuck on "Opening website…"

**It is not your URL, and it is not Render.** `https://htmlabuilder-1.onrender.com` returns
HTTP 200 with the full 79 KB Forge Studio page. The page you see in the APK is generated by
your own server, and the app never navigates away from it because of a scope bug in Nitron.

---

## 1. The page in your screenshot is your own wrapper

`index.js`, live-URL mode, wrote this into the APK as `assets/www/index.html`:

```html
<p>Opening website…</p><p><a href="...">Continue to website</a></p>
<script>window.location.replace("https://htmlabuilder-1.onrender.com");</script>
```

That is exactly what your screenshot shows: unstyled black text, blue link, white background.
So the WebView loaded the local wrapper and **the redirect was cancelled**.

## 2. Root cause: `<meta-data>` is written in the wrong manifest scope

Your `index.js` correctly sets `externalLinks: 'inapp'` (line 335). Nitron correctly turns that
into a manifest tag. But look at where it puts it.

`src/engines/nitronoid/manifest.ts` (pinned commit `d2071302`), end of the template:

```xml
<application ...>
    <activity ...>
        <intent-filter> ... </intent-filter>

${metaDataXml}          <!-- ← INSIDE <activity> -->
    </activity>
</application>
```

`template-src/base/MainActivity.java:358-379` reads it back like this:

```java
ApplicationInfo appInfo = getPackageManager()
    .getApplicationInfo(getPackageName(), PackageManager.GET_META_DATA);
Bundle meta = appInfo.metaData;
if (meta != null) {
    externalLinksMode = meta.getString("nitron.externalLinks", "browser");
    ...
}
```

`ApplicationInfo.metaData` **only contains `<application>`-level `<meta-data>`.**
Activity-level `<meta-data>` lives in `ActivityInfo.metaData`. There is no `<application>`-level
meta-data at all, so `appInfo.metaData` is `null`, the `if` block never runs, and every setting
keeps its default — including `externalLinksMode = "browser"`.

Then `shouldOverrideUrlLoading()` (MainActivity.java:~118) does this to your redirect:

```java
if ("inapp".equals(externalLinksMode) || allowedHosts.contains(host)) return false;  // never taken
if (request.isForMainFrame()) { openInSystemBrowser(uri); return true; }             // ← this runs
```

`return true` **cancels the WebView navigation**. Both the JS `location.replace()` and the
`<meta http-equiv="refresh">` fallback are renderer-initiated main-frame navigations, so both
get handed to the system browser and both are cancelled. The WebView stays on the wrapper
forever. That is your bug.

### Proof — same project, same config, real compiled APKs

`aapt2 dump xmltree app.apk --file AndroidManifest.xml`

**Before (stock Nitron):** `meta-data` is nested *inside* `activity`:

```
E: application (line=11)
    E: activity (line=19)
        E: meta-data (line=30)
        E: meta-data (line=33)
          A: name="nitron.externalLinks"
```

**After (patched):** `meta-data` is a *sibling* of `activity`, under `application`:

```
E: application (line=11)
    E: activity (line=19)
    E: meta-data (line=34)
    E: meta-data (line=37)
      A: name="nitron.externalLinks"
      A: value="inapp"
```

## 3. The same bug was silently breaking four other settings

Because the whole bundle was `null`, these were also ignored in every APK you ever built:

| Setting you send | Actually used |
|---|---|
| `webview.externalLinks: 'inapp'` | `browser` — **your live-URL bug** |
| `webview.allowedHosts: [...]` | empty |
| `webview.backButton: 'exit'` | `history` |
| `webview.clearCacheOnStart: true` | `false` |
| `splashScreen.backgroundColor` | `#FFFFFF` (white launch flash) |

`statusBar` was unaffected — your system-bars patch uses a native bridge, not meta-data.

## 4. What I changed

Three files, in `forge-fix/`:

**`scripts/patch-nitron-runtime-config.js`** (new) — fixes both sides:
1. `manifest.ts`: emits the `nitron.*` `<meta-data>` under `<application>`.
2. `MainActivity.java`: adds `forgeRuntimeMetaData(ApplicationInfo)`, which merges
   `ApplicationInfo.metaData` **and** `ActivityInfo.metaData` (activity wins), and uses it at
   both read sites (`readMetaData()` and `setupSplashScreen()`).

Fixing both means the config is honoured regardless of which scope a future Nitron revision
uses. The script is idempotent and throws on an unrecognised template rather than silently
shipping an unpatched shell — same contract as your other patch scripts.

**`Dockerfile`** — adds the patch step *before* `npm run build` (it edits TypeScript) and
*before* `prepare-template.js` (it edits Java), plus two new build assertions:
- `grep -q FORGE_RUNTIME_METADATA_PATCH dist/cli.js`
- `classes.dex` must contain `forgeRuntimeMetaData` and `getActivityInfo`

**`index.js`** — live-URL mode only:
- adds `allowedHosts: [targetHost]` as a second safety net
- adds `splashScreen: '#0b0d14'` so launch doesn't flash white (works now that meta-data is read)
- replaces the bare white wrapper with a dark loading screen matching Forge, a spinner, a
  "site may be waking up" note after 12 s (free Render instances cold-start), and a styled
  Continue button. Navigation mechanism is unchanged (JS `replace` + meta-refresh fallback).

Nothing else in `index.js` was touched. File-upload and ZIP modes are unchanged.

## 6. Deploy

The native shell is compiled into the image, so **restarting Node is not enough**.

1. Copy `forge-fix/scripts/patch-nitron-runtime-config.js` into your repo's `scripts/`.
2. Replace `Dockerfile` and `index.js` with the ones in `forge-fix/`.
3. Rebuild the image **without cache** for the Nitron layers:
   `docker build --no-cache -t forge-studio .`
4. Redeploy, then **generate a brand-new APK**. Already-installed APKs never change.
5. Uninstall the old app first (package id stays the same, but a clean install avoids a stale
   WebView cache), then install the new APK.

Expected: dark loading screen for a moment, then the live site inside the app.

## 7. One limitation you should know about (not fixed here)

After the redirect succeeds, the WebView is on `https://htmlabuilder-1.onrender.com`, which is
**not** the app origin (`https://appassets.androidplatform.net`). Nitron deliberately gates its
bridge on the app origin, so on the remote page:

- ✅ system bars stay hidden — Activity-level, re-applied natively in `onResume()`
- ✅ light/dark theme still correct — chosen natively before the WebView is created
- ✅ startup permission prompt still fires — the shim runs on the wrapper before navigating
- ❌ `window.Nitron.*` / `Nitron.plugins.Permission.*` calls are ignored (`isAppOriginNow()`)
- ❌ `getUserMedia()` mic/camera is **denied** — `onPermissionRequest()` grants app origin only
- ❌ geolocation prompt denied

If your live-URL apps need mic/camera/permissions **on the remote page**, the proper fix is to
drop the wrapper entirely: load the remote URL directly as the WebView's first page
(`webView.loadUrl()` bypasses `shouldOverrideUrlLoading` completely) and treat your configured
host as a trusted origin. That is a deliberate security trade-off — it gives your site access
to the native bridge — so I left it out. Say the word and I'll implement it.
